## Что можно подготовить и что нельзя активировать

После отдельного implementation authorization B01–B03 могут создать consumer schema/read/export/load modules и qualified real information panel без calendar или room assertions. Реальное empty/partial/seed состояние показывается явно. Текущее observed dataset имеет **0 mapped lessons из 745** и **0 confirmed date lessons**; это допустимый результат read-only information phase, не повод наполнить полигоны по guessed room codes.

Уверенная scheduled highlighting eligibility — conjunction:

```text
validated source course/revision/provenance
AND accepted source freshness policy
AND verified calendar/date applicability
AND resolved parity/subgroup applicability
AND established upstream building authority
AND accepted room catalog/binding authority
AND eligible map region without binding conflicts
```

User-confirmed catalog может удовлетворить последний identity authority gate только после D7 acceptance и с честным label. Для 81 candidate records даже после D7 нужен D13. Не проверенные 101/103/106 composites не превращаются в verified-binding; composite outlines существующего catalog сохраняются целиком.

## Требования к review/rollback и сохранению поведения

MAP-02B следует использовать latest approved UI baseline, а не переключаться на stale local main. Remote main в MAP-02A проверен отдельно и diverged от UI-FIX-B commit. Любое последующее baseline движение должно быть заново зафиксировано, без reset пользовательского worktree.

`map-data.js`, polygons, historical IDs, archived graph, floors 2–7, first-floor display geometry, `room-identification.js` catalog identities и FIX-01 storage format/key защищены будущим scope по умолчанию. Для caller passing manual bindings в resolver нужно использовать текущие conflict checks, не повышать verification вручную и не заимствовать demoAssociations. Synthetic examples используются исключительно в tests/demo, не в accepted snapshot.

Rollback feature flag возвращает source mode к явно подписанному demo; previous accepted snapshot остаётся отдельно идентифицированным real LKG. Удаление только новых timetable cache keys допускается future rollback contract; существующие bindings не очищаются. Failed parse/export/load never overwrites accepted cache. Невозможность online refresh не оправдывает объединение real и demo records.
